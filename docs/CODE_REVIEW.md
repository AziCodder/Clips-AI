# Жёсткий код-ревью проекта CLIP AI / Автоматизация 2

Дата: 2025-03-02. Обзор: backend (FastAPI), frontend (React), gpu-worker, transcribe_video.py, инфраструктура.

---

## Что сделано хорошо

- **Структура backend:** разделение на api/v1, db/models, services, tasks — понятно и масштабируемо.
- **Async БД:** FastAPI + asyncpg + SQLAlchemy 2 async — корректный выбор для I/O-bound API.
- **JWT + зависимости:** `get_current_user`, `verify_gpu_api_key` вынесены в deps, переиспользуются.
- **GPU job flow:** lease через `with_for_update(skip_locked=True)`, TTL, reaper — логика очереди продумана.
- **Схемы Pydantic:** VideoRead, VideoDetailRead, GpuJob* — типизация ответов API на месте.
- **Транскрипция (transcribe_video.py):** проверка зависимостей в начале, fallback субтитры → скачивание → WhisperX, выход с кодом при ошибках — предсказуемое поведение CLI.
- **Frontend:** единый axios client с interceptors для токена и 401 → редирект на логин.
- **Рендер клипов:** учёт нагрузки (psutil.cpu_percent), semaphore, ThreadPool — разумно для CPU-bound.

## Критичные проблемы

### 1. Секреты в репозитории (безопасность)

**Файл:** `infra/env/cpu-backend.env`

В файле лежат реальные значения:
- `S3_ACCESS_KEY`, `S3_SECRET_KEY`
- `TELEGRAM_BOT_TOKEN`
- Пароли/ключи БД

**Проблема:** любой с доступом к репо (или утёкший дамп) получает доступ к S3, Telegram-боту и БД.

**Что делать:** убрать файл из git (добавить в .gitignore), использовать переменные окружения или секрет-менеджер (Vault, облачные Secrets). В репо оставить только `*.env.example` без секретов.

---

### 2. Presigned URL для клипа не привязан к video_id (уязвимость доступа)

**Файл:** `cpu-backend/app/api/v1/media.py`, эндпоинт `get_presigned` (строки 19–34).

Для `asset_type == clip_video` проверяется только наличие `clip_id` и что у ClipJob есть `s3_clip_key`. **Не проверяется, что клип принадлежит переданному `video_id`.**

Сценарий: пользователь знает `clip_id` чужого клипа (другое видео). Вызывает:
`GET /media/presigned?video_id=СВОЁ_ВИДЕО&asset_type=clip_video&clip_id=ЧУЖОЙ_КЛИП`. Получает presigned URL и может скачать чужой клип.

**Что делать:** при выдаче presigned для `clip_video` загружать ClipJob с join на Highlight и проверять `Highlight.video_id == video_id`. Иначе возвращать 404.

---

### 3. CORS в production с заглушкой домена

**Файл:** `cpu-backend/app/main.py`, строки 45–51.

В production задано `allow_origins=["https://your-domain.com"]`. Если не заменить на реальный домен, фронт с другого домена получит CORS-ошибки.

**Что делать:** вынести домен фронта в конфиг (например `FRONTEND_ORIGIN`) и подставлять в `allow_origins`.

---

### 4. Ошибки списка видео не показываются пользователю (Frontend)

**Файл:** `frontend/src/pages/Videos/VideosPage.tsx`, функция `load` (строки 24–39).

В `load()` нет `catch`. При падении `videosApi.list()` (сеть, 500) срабатывает только `finally` → сбрасывается loading, список остаётся пустым или старым. Пользователь не видит ни сообщения об ошибке, ни возможности повторить.

**Что делать:** завести состояние `error: string | null`, в `catch` устанавливать его из `err.response?.data?.detail` или `err.message`, в разметке показывать блок с ошибкой и кнопкой «Повторить».

## Серьёзные проблемы

### 5. Глотание исключений без логов

**Файлы и места:**

- `cpu-backend/app/main.py`, lifespan (строки 30–34): `except Exception: pass` при закрытии сессии бота — при ошибке закрытия никто не узнает.
- `cpu-backend/app/api/v1/videos.py`: несколько `except Exception: pass` при удалении в S3 и в debug-логе (строки 275, 314, 356).
- `cpu-backend/app/api/v1/media.py`, get_clips (строки 124–126): `except Exception: pass` при presign — при сбое S3 клиент просто получит `presigned_url: null` без причины.

**Проблема:** отладка в проде усложняется, метрики/мониторинг не видят сбои.

**Что делать:** минимум — логировать `log.warning("...", exc_info=True)`. По возможности — возвращать пользователю понятный код/сообщение или повторять операцию.

### 6. Поиск по названию: LIKE-инъекция и лишние совпадения

**Файл:** `cpu-backend/app/api/v1/videos.py`, строка 75.

```python
stmt = stmt.where(Video.title.ilike(f"%{q}%"))
```

Параметр `q` подставляется в шаблон как есть. Символы `%` и `_` в SQL LIKE — wildcards. Запрос `q=%` вернёт все видео; `q=___` — все с названием длиной не меньше 3 символов. Это не SQL-инъекция (параметр не в сыром SQL), но неконтролируемое расширение поиска и возможный DoS (тяжёлые запросы).

**Что делать:** экранировать в строке поиска `%` и `_` (например заменить на `\%` и `\_` и задать `escape='\'` в ilike) или использовать только точные/нормализованные подстроки.

### 7. Дебаг-лог с захардкоженным sessionId и путём

**Файл:** `cpu-backend/app/api/v1/videos.py`, функция `_debug_log_delete_video` (строки 257–277).

- Используется `os.environ.get("DEBUG_LOG_PATH", "debug-31c580.log")` — дефолт с идентификатором «31c580».
- В payload жёстко прописано `"sessionId": "31c580"`.

В продакшене это мусор в коде и риск писать в неожиданную файловую систему. В docker-compose уже задаётся `DEBUG_LOG_PATH` — дефолт в коде лучше убрать и не оставлять sessionId в коде.

**Что делать:** убрать дебаг-логирование из продакшен-ветки или вынести в отдельный логгер с уровнем DEBUG и без дефолтного пути/идентификатора в коде.

### 8. Нет глобального обработчика исключений в FastAPI

**Файл:** `cpu-backend/app/main.py`.

Необработанные исключения (в т.ч. из зависимостей и сервисов) отдаются как стандартный JSON FastAPI. Формат ответов об ошибках может отличаться от вашего (например от Pydantic/HTTPException). Сложнее единообразно обрабатывать ошибки на фронте и в логах.

**Что делать:** зарегистрировать `@app.exception_handler(Exception)` (и при необходимости более узкие типы), логировать исключение и возвращать единый формат тела ошибки (например `{ "detail": "...", "code": "internal_error" }`).

### 9. Approve API: путаница id на фронте

**Файл:** `frontend/src/lib/api/client.ts`:  
`approve: (id: string, status: ...) => api.post(\`/approvals/${id}\`, ...)`

**Файл:** `cpu-backend/app/api/v1/approvals.py`: эндпоинт `POST /approvals/{video_id}` — в path ожидается **video_id**, не approval_id.

В коде страниц вызовов `approve` сейчас нет. Если позже вызовут `approve(approval.id, ...)` вместо `approve(video.id, ...)`, запрос уйдёт с неверным id и бэкенд вернёт 404.

**Что делать:** в клиенте переименовать параметр в `videoId` и в JSDoc/типах явно указать: «id видео, для которого выносится решение». На бэкенде можно оставить как есть (video_id семантически верен).

### 10. Reaper и повторная постановка в очередь: гонка при масштабировании

**Файл:** `cpu-backend/app/tasks/pipeline_tasks.py`, `task_reaper` (строки 354–396).

Рейпер снимает lease у «протухших» джобов и переводит их в QUEUED без дополнительной блокировки. При нескольких воркерах Celery или частом вызове теоретически возможна гонка: два процесса видят один и тот же stale job и оба пытаются его перевести в QUEUED. Сейчас рейпер вызывается по расписанию, конкуренция ограничена, но при росте нагрузки это может проявиться.

**Что делать:** при масштабировании — блокировка по job_id (Redis lock) или обновление «только если lease_expires_at ещё не изменился» (оптимистичная блокировка).

### 11. delete_video(scope="video_only"): объект video не обновлён после commit

**Файл:** `cpu-backend/app/api/v1/videos.py`, строки 348–357.

После `video.description = ""` и `await db.commit()` нет `await db.refresh(video)`. Ответ 204 без тела, поэтому клиенту всё равно. Но если позже в том же обработчике или в мидлваре будет использоваться `video`, он может быть в устаревшем состоянии.

**Что делать:** после commit при `scope="video_only"` вызвать `await db.refresh(video)` для консистентности, либо явно не использовать `video` после commit.

---

### 12. task_render_clips_batch не идемпотентен

**Файл:** `cpu-backend/app/tasks/pipeline_tasks.py`, `task_render_clips_batch` (строки 345–322).

Задача берёт все видео в статусе ANALYZED и для каждого highlight создаёт **новый** ClipJob. Нет проверки «для этого highlight уже есть ClipJob (DONE/FAILED)». В нормальном потоке видео переводится в CLIPS_READY и повторно не обрабатывается. Но при ручном сбросе статуса видео обратно в ANALYZED и повторном запуске задачи появятся дубликаты ClipJob для тех же highlights.

**Что делать:** перед созданием ClipJob проверять: для данного highlight ещё нет записи в ClipJob (или нет со статусом DONE). Создавать только недостающие.

### 14. run_async в pipeline_tasks

**Файл:** `cpu-backend/app/tasks/pipeline_tasks.py`, строки 18–20.

```python
def run_async(coro):
    return asyncio.get_event_loop().run_until_complete(coro)
```

В коде `run_async` не используется — везде вызывается `asyncio.run(...)`. Либо удалить, либо использовать единообразно и учитывать, что `get_event_loop()` в Python 3.10+ в некоторых контекстах deprecated в пользу `asyncio.run()`.

---

### 15. transcribe_video.py: дефолтный output-dir и мусор в конце

**Файл:** `transcribe_video.py`.

- Строка 384: `default="output"` — относительный путь. При запуске из другой директории выход уйдёт в текущую рабочую папку, а не в «output» относительно скрипта. Лучше явно документировать или использовать `os.path.abspath("output")`.
- Строка 671: `"""текст"""` — мёртвая строка, стоит удалить.

---

### 16. mark_failed: обрезка traceback без учёта границы

**Файл:** `cpu-backend/app/api/v1/gpu_internal.py`, строка 145.

`body.traceback[:500]` — обрезка по длине есть, но при очень большом traceback в лог/БД попадёт обрезанная строка без пометки «обрезано». Для отладки можно добавить суффикс типа `"... [truncated]"` при len(traceback) > 500.

### 17. VideoRead.already_exists и ответ 200 при «уже существует»

**Файлы:** `cpu-backend/app/api/v1/videos.py` (строки 104–105, 141), `cpu-backend/app/schemas/video.py` (поле `already_exists: bool = False`).

При добавлении видео по URL, если оно уже есть, возвращается 200 и `already_exists: True`. Семантика «успех, но ресурс уже был» — допустима, но не все REST-практики так делают (часто 409 Conflict). Фронт обрабатывает `already_exists` и показывает сообщение — связка согласована. Оставить как есть можно, но стоит явно описать в API-документации.

---

### 18. GPU worker: sys.exit(1) при таймауте джоба

**Файл:** `gpu-worker/worker/main.py`, строки 172–185.

При превышении JOB_MAX_DURATION_SEC воркер вызывает `mark_timeout` и `sys.exit(1)`. По задумке инстанс завершается, оркестратор (например Vast.ai) перезапускает. Это осознанное решение; нужно только убедиться, что в деплое действительно настроен перезапуск и что нет потери других джобов в том же процессе (сейчас воркер обрабатывает один джоб в потоке, при exit все потоки завершаются — учтено).
